# 手写识别引擎替换方案（搜狗 → HCCR / Ismantic-Handwritten）

> 本文档描述 yuyansdk 手写识别引擎的改造目标、当前进度与后续实施步骤。
> 目标：用开源的 **Ismantic/Handwritten**（NCNN 推理）替换现在的**搜狗预编译手写库**，
> 解决其闭源、体积大、未满足 16KB 内存页对齐、存在授权/合规风险等问题。

---

## 一、背景与现状

### 1.1 当前搜狗方案的问题

yuyansdk 目前依赖搜狗预编译手写库，涉及以下 4 个 `.so`（仅存在于 `arm64-v8a`）：

```
libs/arm64-v8a/libhandwriting.so
libs/arm64-v8a/libSogouShell.so
libs/arm64-v8a/libgpen_handwriter.so
libs/arm64-v8a/libhwInterface.so
```

配套的资源位于 `src/main/assets/hw/`（`sogouhw/` 模型、`license/` 授权文件等）。

问题点：

- **闭源、不可审计**：编译产物 + 授权文件（`license.temp`、`pubkey.pem`），无法确认数据/隐私行为。
- **16KB 内存页对齐不达标**：`libSogouShell.so` / `libhandwriting.so` / `libhwInterface.so` 的对齐单位为 `0x1000`，不满足 Android 16（API 36）对 64KB/16KB page 原生库的对齐要求，属于厂商需更新的黑盒依赖。
- **多 ABIs 支持不完整**：仅 `arm64-v8a` 有搜狗库，`armeabi-v7a` / `x86` / `x86_64` 缺失，模拟器与旧设备不可用。
- **调用链是黑盒 `external fun`**：见 [HandWriting.kt](../src/main/java/com/yuyan/inputmethod/core/HandWriting.kt)，通过 `System.loadLibrary("handwriting")` + 一组 external（`inputHWPoints` / `getCandidates` / `initWithDirectory` 等）完成识别，无法自定义纠错、候选数、输入口径。

### 1.2 已完成的替代方案集成（基线）

已把开源项目 [Ismantic/Handwritten](https://github.com/Ismantic/Handwritten)（NCNN 单字手写识别）接入 yuyansdk 并跑通编译：

| 内容 | 路径 |
| --- | --- |
| Java 接口 | `src/main/java/com/shiyu/handwritten/runtime/HCCRRecognizer.java` |
| JNI 实现 | `src/main/cpp/hccr_jni.cc` |
| 预处理（与训练/ Python demo 一致） | `src/main/cpp/preprocess.c` / `preprocess.h` |
| CMake 构建 | `src/main/cpp/CMakeLists.txt` |
| 模型参数（INT8） | `src/main/assets/hccr_model.int8.ncnn.param` / `.bin` |
| 字符表 | `src/main/assets/hccr_charset.json` |
| ABI 过滤 | `build.gradle.kts` 中 `ndk.abiFilters`（arm64-v8a / armeabi-v7a / x86 / x86_64） |
| 工具链 | NDK `30.0.14904198`、CMake `3.22.1+` |

关键接口（HCCRRecognizer）：

```java
HCCRRecognizer(AssetManager assets, String paramName, String binName, String charsetName)
          .preprocess(byte[] gray, int w, int h, float[] output)   // gray -> float[64*64]
          .predict(float[] input, int k)                            // -> Result[]{text, probability}
```

预处理口径（`preprocess.h`）：

```
灰度图(255=白底, 0=黑笔画) → 找前景 bbox(像素<220) → 裁切 + 长边等比缩到 56
→ 居中放到 64×64 白底 → 翻转 + 归一化 → float[64*64]（stroke=高值）
```

## 二、后续实施步骤

### 阶段一：替换调用链（核心改造）

把 [HandWriting.kt](../src/main/java/com/yuyan/inputmethod/core/HandWriting.kt) 的搜狗 `external fun` 调用链替换为 `HCCRRecognizer`，同时改造 [HWEngine.kt](../src/main/java/com/yuyan/inputmethod/HWEngine.kt) 的 `recognitionData`。

#### 1）接入 HCCRRecognizer 生命周期

- 在 `HWEngine` 中初始化一次并持有单例（与 Rime 引擎一致，避免重复加载 4MB 模型）。
- 加载方式：`HCCRRecognizer.loadNativeLibrary("<生成的 jni so>")` + `new HCCRRecognizer(context.assets, "hccr_model.int8.ncnn.param", "hccr_model.int8.ncnn.bin", "hccr_charset.json")`。
- 提供 `close()` 释放（`nativeRelease`）。

#### 2）把笔画轨迹渲染成 64×64 灰度图

当前 `HWEngine.recognitionData` 拿到的是 `MutableList<Short?>`（打点序列），经 `inputHWPoints` 直接喂给搜狗。替换方案需要先把笔画画到白底 Bitmap，再转成灰度字节：

- 参照 [Handwritten 的 HandwritingView 设计](https://github.com/Ismantic/Handwritten)（`renderTargetSize=360`、`renderStrokeRatio≈4.4%`、**关闭 anti-alias**、使用 `lineTo` 直线段，与 HWDB 数位板训练分布对齐）。
- 渲染后：

```kotlin
val bmp: Bitmap        // 白底黑笔画
val w = bmp.width; val h = bmp.height
val gray = ByteArray(w * h)   // 0 = 笔画(黑), 255 = 白
bmp.getPixels(pixels, 0, w, 0, 0, w, h)
for (i in pixels.indices) gray[i] = (255 - Color.luminance(pixels[i])).roundToInt().toByte()

val input = FloatArray(64 * 64)
recognizer.preprocess(gray, w, h, input)
val results = recognizer.predict(input, k = candidateCount)
```

#### 3）候选词装配

`predict` 返回 `Result[]{text, probability}`，需按现有 `CandidateListItem{text, pinyin}` 结构装配，并走原有 `pinyin4j` 转注音逻辑复用 [HWEngine.kt](../src/main/java/com/yuyan/inputmethod/HWEngine.kt) 的候选回调 `IHandWritingCallBack.onSucess`。

#### 4）线程与性能

- 推理放后台线程（复用现有线程池工具），避免阻塞 IME 主线程。
- 模型仅加载一次；命中缓存（相同笔画不做重复推理）。
- NCNN 已禁用 Vulkan（CPU 推理），确认在低端机上单次前向延迟可接受。

#### 5）候选数与纠错

- 由 `predict(k)` 控制候选数；可结合 `probability` 做阈值过滤与 Top-K 候选排序。

### 阶段二：移除搜狗库与相关资源

全部替换并验证通过后删除：

- 删除 `libs/arm64-v8a/lib{handwriting,SogouShell,gpen_handwriter,hwInterface}.so`。
- 删除 `src/main/assets/hw/` 整个目录（`sogouhw/`、`license/`、`PYDict/`、`license.temp`）。
- 删除 `HandWriting.kt` 中搜狗 `external fun` 与 `System.loadLibrary("handwriting")`（保留类，改由 `HCCRRecognizer` 承载）。
- 确认 `build.gradle.kts` 的 `sourceSets.offline.jniLibs.srcDirs("libs")` 只保留 `libyuyanime.so`（Rime 核心链）相关产物。

> ⚠️ 前置条件：阶段一在真机（含手写键盘）完整回归通过后再移除，避免手写功能断档。

### 阶段三：NCNN 预编译库获取与构建说明

`ncnn-android` 是**构建期依赖**（90MB，已被 `.gitignore` 排除），clone 后需自行下载解压：

- 从 ncnn 官方 releases 下载 `ncnn-YYYYMMDD-android-vulkan.zip`，解压到 `third_party/ncnn-android/`，目录结构需满足：

```
third_party/ncnn-android/<ABI>/lib/cmake/ncnn/ncnn-config.cmake
third_party/ncnn-android/<ABI>/lib/*.a
third_party/ncnn-android/<ABI>/include/ncnn/*.h
```

- `abifilters` 当前为 4 个 ABI（arm64-v8a / armeabi-v7a / x86 / x86_64），下载的 ncnn 包需包含对应 ABI；若仅需真机，可收紧为 `arm64-v8a` 以减少体积。
- 也可改用 AAR 依赖（`com.tencent.ncnn:ncnn:<ver>`），减少手工解压，但需确认 CMake `find_package(ncnn)` 适配。

### 阶段四：验证与持续维护

- **一致性回归**：用 [Ismantic/Handwritten 的 Python 一致性测试](https://github.com/Ismantic/Handwritten)（`test/test_preprocess.py` 等）保证 `preprocess.c` 与 `normalize.py` 字节级一致；修改 `preprocess.c` 后需同时跑 Python 测试与 Android 构建。
- **准确率对比**：同一批手写样本分别经旧搜狗库与新 HCCR 识别，比对条件（识别率、Top-1/Top-K、候选质量）。不只看能否加载模型，必须对比识别效果。
- **16KB 对齐复查**：`libhccr_jni.so`（或产物名）需满足 16KB page 对齐要求（`readelf -l` 校验 LOAD segment 对齐）。
- **多 ABI**：确认 `armeabi-v7a` / `x86` / `x86_64` 均可构建出可用的 `hccr_jni`，补齐原搜狗缺失的 ABI。
- **模型升级通道**：模型权重与字符表独立于代码存放于 assets，替换模型/字符表即可更新手写字库，无需改代码（`hccr_charset.json` 的 `char_to_idx` / `num_classes` 需与模型输出一致）。

## 三、风险与备选

| 风险 | 缓解措施 |
| --- | --- |
| HCCR 单字模型候选质量低于搜狗 | 用真实手写样本回归对比；必要时引入语言模型重排候选 |
| 笔画渲染口径与训练分布不一致导致识别率下降 | 严格复用 Handwritten 的渲染参数（360 目标尺寸 + 4.4% 笔宽 + 无 AA） |
| 推理耗电/性能 | CPU 线程数 `num_threads=4`，必要时打开 Vulkan 计算 / FP16 |
| 多字连续书写 | HCCR 为单字识别，需要在自定义层做切分后再逐字识别 |
| 中文动态连笔 | 依赖模型泛化；可借助 NCNN 重新训练/微调自有数据 |
